Federate projects around work and evidence; do not centralize their product meaning in AIDE.

## Scope and authority

This is a proposed design contract. It is not runtime activation, target mutation permission or a claim that every requirement is implemented. Existing queue, policy, schemas, source and qualification records retain their owners.

## Design

A domain bridge maps WorkUnits, capability invocations, native result/refusal, diagnostics, evidence and domain transaction bundles. The project owns canonical execution and acceptance. AIDE can coordinate a ScreenSave visual proof, Eureka provenance check, MIR compatibility test or Dominium validation without rewriting each into one generic result ontology.

Canaries are chosen for actual needs and contrasting constraints. MIR read-only adoption and update-context work can produce immediate utility; ScreenSave provides deterministic visual and native legacy cases; Eureka exposes observation-versus-acceptance boundaries; Dominium/Workbench tests domain-native authoring. FacMan and Universal Setup/Launcher contribute lifecycle/session mechanisms only through selected qualified interfaces. Other projects, including Carbon, remain profile candidates until their own reference oracle exists.

No consumer inherits the producer's acceptance merely by importing a bridge pack. AIDE-side fixture validation is not live project-command success. A correct typed refusal is useful integration evidence but not proof that domain validation ran. Project law and legal permissions remain local. Advanced vehicle, property, voice and hardware profiles must retain independent deterministic safety boundaries; generative output stays a proposal and is not authorized to control safety-critical systems.

## Interface and data boundary

Project identity/revision; domain owner; native command schema; fixed binding; result/refusal map; proof artifact; consumer admission; compatibility; target release gate.

Reuse existing protocol owners before creating a new public kind. Wire objects, internal values, semantic validation, policy evaluation, fixtures and renderings remain separate. New fields below are design requirements, not an automatic wire-schema amendment.

## Proposed normative requirements

### UR-DOMAIN-01 — Domain-owned semantics

AIDE bridges MUST preserve project-native commands, mutation meaning, validation and release authority.

### UR-DOMAIN-02 — Consumer admission

Each consumer MUST independently admit imported bridge/package artifacts for its own scope.

### UR-DOMAIN-03 — Fixture versus live

Bridge reports MUST distinguish fixtures, real command-boundary invocation, typed refusal and actual domain success.

### UR-DOMAIN-04 — Fixed initial operations

Initial project adapters SHOULD expose fixed typed operations with contained outputs, not unrestricted generic exec.

### UR-DOMAIN-05 — Canary priority is policy

Portfolio canary order MUST be selected from current project needs and declared diversity rather than historical chat order.

### UR-DOMAIN-06 — No runtime dependency transfer

Target product executables MUST NOT require AIDE solely because AIDE helped develop or install them.

### UR-DOMAIN-07 — Safety-critical separation

Experimental physical-world profiles MUST NOT grant generative models direct safety-critical control or bypass domain-certified authorities.

## Acceptance design

The linked cases are **not run**. Each requires a pinned subject and environment, observed effects and an independently defined oracle. Package-local JSON or Markdown validation does not execute these scenarios.

| Case | Adversarial stimulus | Required observation |
|---|---|---|
| `UC-DOMAIN-01` | A generic bridge attempts to accept artistic quality for ScreenSave. | The decision remains with the project-owned proof and review boundary. |
| `UC-DOMAIN-02` | A producer marks its artifact accepted. | The target does not automatically activate it. |
| `UC-DOMAIN-03` | A live command returns refusal. | The capability label does not claim aggregate validation success. |
| `UC-DOMAIN-04` | A canary requires one native validator. | The adapter admits that command rather than an arbitrary shell surface. |
| `UC-DOMAIN-05` | MIR becomes the operator-prioritized practical canary. | The plan can prioritize it without erasing ScreenSave or Dominium qualification needs. |
| `UC-DOMAIN-06` | Remove optional AIDE development tooling. | The qualified target product remains operable. |
| `UC-DOMAIN-07` | A voice or vehicle integration proposes privileged control. | The deterministic safety boundary remains authoritative and unsupported actions refuse. |

The proposed requirements and acceptance designs are retained inline above. The original bulk registers remain external review inputs; see [import status and source identities](../draft-import.md).

## Delivery boundary

Implement this contract only through a source-bound, queue-admitted vertical slice with existing consumers or a contrasting fixture. Separate source presence, local test results, operational qualification, activation and release support in the closeout record. Optional profiles do not become prerequisites for smaller supported profiles.
