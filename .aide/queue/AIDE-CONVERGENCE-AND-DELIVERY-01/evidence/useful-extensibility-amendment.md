# Useful extensibility: amendment to the existing delivery plan

Prepared 2026-10-17 from the owner's three supplied reviews and current source.
This is a planning amendment, not a new adopted specification, capability claim,
task queue or grant to install, contact peers, execute models or alter targets.
P0-P11 and C identifiers retain their existing meaning and owners. The four
relationship types in `docs/roadmap/development-workflows.json` remain distinct:
implementation prerequisites, activation gates, qualification gates and preferred
sequence. This document adds no blanket programme dependency.

## What the current evidence establishes

Lite 1.0.0 is published for its recorded local Windows profile. Source, installed
fixtures and the new machine have their own evidence; a new source commit is not
a new product release. The native DiskEd selected-export preparation now has an
accepted fixture outcome: 158 passes, two unavailable original symlink checks,
and completed bounded continuation. Its first wrapper failure is preserved.
DiskEd application/adoption, automatic owner-to-owner delivery, broader protected
editing and whole-task efficiency are still unproven. The long-term platform has
no defensible single completion percentage.

Relevant existing source boundaries:

- `.aide/scripts/aide_lite.py`: task identity, inspection, context and CLI owners.
  `command_task_current` currently prints only task ID and status. Existing records
  contain substantially more useful continuation information.
- `core/runtime/integration_broker/service.py`: reviewed candidate integration,
  verification and exact `refs/heads/dev` authority. It is not a generic inbox.
- `core/interop/mcp_server_contract.py`: contract projections, explicitly excluding
  callable tools, startup and dispatch. A protocol catalogue is not live delivery.
- `specs/control-plane/engineering/module-and-implementation-boundaries.md`:
  proposed modular-monolith design, explicitly not an adopted implementation grant.

## Architecture refinements to carry into bounded work

One authoritative owner per decision/state field; one declared meaning per
contract version; multiple conformant implementations. Keep domain acceptance in
each project. Sender work, dependency request, receiver-native work, attempts,
integration and adoption are linked identities. They need not share one ID or one
storage format. Independent semantic test oracles remain independent.

Keep a lightweight local product and optional active runtime. Pure semantic and
validation code should not require provider SDKs, editors, a server or a specific
self-hosting queue path. Start in the existing implementation. Extract only when
characterized behavior and an actual dependency, security, compatibility or
ownership need justify it. A process boundary must earn its startup, operational
and deployment cost. Disabled adapters must not import optional SDKs or start
services; removal must leave history readable and supported continuation possible.

Extend existing work/context/execution records to distinguish the requested,
resolved/admitted and observed execution recipe. Bind request revision, native
work references, source/context, selected skill/harness/host/model configuration,
disclosure and effect scope, resource caps, checks, completion obligations and
recovery. This is not permission to introduce a universal replacement envelope.

Repository tailoring needs typed composition. Mandatory constraints combine;
effective authority is the intersection of applicable grants and restrictions;
limits respect applicable caps and shared reservations; preferences have explicit
precedence; components merge by stable identity with explicit opt-outs. Observed
capabilities and learned suggestions never confer permission. Explain each
effective value and retain migration/rollback for a changed profile.

Version schemas and adapter contracts; preserve safe optional unknown data and
refuse unknown required execution semantics. Test replacement and degraded modes,
not just initial installation. Derive distributions from qualified source or
explicitly tested compatibility adapters. Do not manufacture uniform T/L support.

## Coordination details required for the first real loop

The existing integration broker retains its reviewed-candidate gate. Request
intake/delivery should use existing work/ownership primitives through a narrow
boundary, not weaken that gate. Define state ownership before adding persistence.
Acceptance binds a request revision; amendments need attributed reconciliation.
Use durable intent and deterministic operation IDs when a local request and a
native target record cannot be committed atomically. Same ID/same body reuses;
same ID/different body conflicts. Timeout after an effect triggers inspection.

Separate delivery, admission, execution, outcome, completion obligations and effect
certainty in the view. Requested integration, publication and adoption remain
separate obligations. Cancellation must account for worker quiescence, effects and
other consumers. Detect dependency cycles and stale owners. Bound attempts,
retry deadlines, fan-out, message/artifact sizes and notifications. Idle waiting
must not repeatedly invoke models. GitHub projects remote collaboration and actual
ref/release evidence; it does not act as a live process lock.

First prove harmless delivery, then a disposable relocation fixture, then any
separately authorized real move. Preserve active workspaces and reserve destructive
operations to their actual owners. A reservation alone does not constrain an
unrestricted external shell. Do not promise universal exactly-once effects.

## Intelligence, learning, performance and old machines

Intelligence should improve a concrete decision: where behavior belongs, what
already exists, which consumers may break and which checks matter. Use repository
facts and bounded retrieval before broad semantic indexing. Distinguish known
absence, not found, unindexed and stale; an omitted result is not proof of absence.
Keep private context within authorized boundaries and show selection reasons.

Self-improvement starts with a source-linked lesson or candidate regression,
helper, context rule or skill adjustment. Compare against a baseline, change one
major factor at a time, confirm on separate tasks, retain negative results and
promote only accepted improvements. The candidate cannot weaken its own evaluator,
raise its authority or silently change routing. Retire stale lessons. Weight
training is optional and is not required for useful learning.

Measure startup/idle work, peak memory, accepted-outcome latency, retained growth,
model/review usage coverage and human interventions. Cache by actual relevant
inputs; invalidate only affected evidence. Use incremental/on-demand indexing,
bounded logs and backpressure. Prefer a warm capable worker when transfer overhead
outweighs another worker. These choices need measurements, not assumed savings.

Vintage machines may remain readers, native build endpoints or offline companions
while a modern host handles inference and coordination. Qualify a contrasting
bounded bundle profile with filename/encoding/path mapping, stale-base detection,
altered/truncated-transfer refusal and required-unknown semantics. New machines,
models and editors add qualified adapters; neither all-host parity nor a mandatory
runtime rewrite follows. A small modern GPU is not evidence of model capability;
measure an exact available model/backend recipe before assigning it work.

## Next bounded preparation and stop conditions

The companion `current-view-brief.md` identifies existing code/test owners and
acceptance for one read-only current-view increment. It is not implementation
admission. Native adoption requires its own current target evidence. Stop each
bounded experiment at its declared result or terminal prerequisite; continue
independent work. Do not reopen unchanged qualification or generate another
replacement specification pack. The campaign succeeds through accepted useful
work, preserved continuity and reduced repeated effort, not architecture volume.
