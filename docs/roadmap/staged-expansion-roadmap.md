# AIDE Staged Expansion Roadmap

## Purpose

This document keeps later candidate tracks visible without promoting them into current implementation scope.

## First Stack

The reboot foundation target is Contract + Harness + Compatibility + Dominium
Bridge. Q01 documented that target; later queue records establish bounded source
and review. It is not a published release claim.

## Deferred Expansion Tracks

- Runtime: bounded worker/broker foundations exist; generalized service/fleet behavior needs separate qualification.
- CLI/Service: local helper CLI exists; managed service deployment remains a later profile.
- Commander: deferred product/control surface, not Q01 scope.
- Mobile: deferred host or app family, not Q01 scope.
- IDE Hosts: future host-family work after the reboot model and compatibility baseline are reviewed.
- Pack/Skill/Workflow IR: candidate intermediate representations for later design and artifact work.
- GStack/reference imports: candidate reference import track after design-mining and compatibility evidence mature.
- Provider adapters and app surfaces: deferred until specific queue items authorize them.

## Promotion Rule

A deferred track becomes active only when a later queue item defines scope, allowed paths, evidence, validation, and review gates. Until then, references to these tracks are future intent, not implemented reality.

## Operational and later-profile gates

| Track | Required evidence before its claim |
|---|---|
| Outer client | Actual application and model editing routes, effective task scope, allowed edit/check/retirement and denied-route fixtures |
| Worker/model replacement | Deterministic path plus two materially different real bindings; same task semantics and authority; separately authorized model effects |
| Networked execution | Admitted node identity, current ownership generation, cancellation, duplicate/uncertain-effect and partition/reconnect cases |
| Resource residency | Backend-specific fit/support/performance/permission and measured contention/foreground behavior; explicit enforcement classes |
| Controlled adaptation | Dataset lineage, held-out evaluator ownership, scoped activation, rollback and measured usefulness; training is optional |
| Managed scale/tenancy | Isolation, ownership partitions, authenticated transport, restoration and measured limits for the exact deployment |
| Native/legacy hosts | Exact lane environment, T0–T5 posture, mode and L0–L4 ceiling; thin relay does not inherit modern controller authority |
| Stable Lite publication | Existing bounded profile, historical decisions, required live/matched evidence, exact release review and downloaded consumer checks |

Fleet, training, enterprise scale and every host family do not become mandatory
features of the first local Windows Lite release. No hardware acquisition,
service enrollment, purchases, migrations or active deployments follow from
this candidate table. Prefer one deterministic path and small fault fixtures
before broader operational claims.
